Everyone's Talking About Agents. What Are They, and How Do I Build My Own?

A few months ago I started hearing the word "agent" everywhere. LinkedIn, podcasts, work meetings. Everyone talking about "AI agents" as if it were the next great revolution — but very few people actually explaining what it means in practice.

It took me a while to understand it properly. Not because the concept is hard, but because most explanations fall into one of two extremes: either too abstract to tell you anything useful, or too technical to follow past the first two minutes.

This is the post I wish I had when I started. Let's break it down.

The Difference That Actually Matters: Chatbot vs. Agent

A chatbot responds. An agent acts.

When you ask ChatGPT a question, it gives you an answer. That's it. It doesn't do anything in the real world, doesn't query your systems, doesn't execute tasks. It's a conversation — a very intelligent one, but only a conversation.

An agent, on the other hand, can do things. It can query a database, send an email, run a script, call an API, save a file. It has access to tools, and it uses them to complete objectives.

The difference isn't in the AI model itself — it's the same underlying technology. The difference is in how the system around the model is built.

The Three Ingredients of Any Agent

No matter how complex an agent is, it always has these three components:

1. A model that reasons (the brain). That's the LLM — GPT-4, Claude, Gemini, whichever. Its job is to understand the task, decide what to do, and generate responses. But on its own, it can't do anything outside the conversation.

2. Tools it can use (the hands). These are real functions the model can invoke: query a database, call an external API, read a file, send a notification. The model doesn't execute them directly — it tells the system "I want to use this tool with these parameters," and the system does it.

3. A reasoning loop (the cycle). This is the key part. An agent doesn't respond once and stop. It follows a cycle:

Receives a task
  → Reasons: what do I need to solve this?
  → Uses a tool
  → Observes the result
  → Done? No → keeps reasoning
  → Done? Yes → responds

This loop is what makes it an "agent." It can take multiple steps, adapt to intermediate results, and reach an objective without human intervention at every step.

Real Use Cases — the Ones Already Happening

Enough theory. Here are three concrete examples of the kind of agents being used today.

1. Data monitoring agent

Imagine you have an important metric in your database — daily sales, active users, whatever matters to you. An agent can query that metric every morning, compare it to the previous day, and if there's an unusual variation, send you an alert with context: "Today's sales are 40% below the 7-day average. The most affected products are X and Y." It doesn't just tell you something happened. It explains what happened.

2. Internal support agent

In many companies, the support team answers the same questions over and over: how to reset a password, what's the process for X, where's document Y. An agent connected to the company's knowledge base can answer those questions automatically, query internal systems when it needs real-time data, and escalate to a human only when it genuinely doesn't know the answer.

3. Weekly reporting agent

Every Monday, someone has to put together the weekly report. Data from different sources, an analysis, the key metrics. An agent can do that work: queries the sources, aggregates the data, generates the analysis text, and sends the email. What used to take two hours now happens in five minutes with no supervision.

Let's Look at the Code: a Simple Agent in Python

So it doesn't stay only in theory, here's a real, working example of how to build an agent. Just Python and Claude's API — no frameworks, no black magic.

The idea: an agent that has access to two tools — querying the weather and doing math. We give it a task in plain language and it decides how to solve it.

import anthropic
import json

client = anthropic.Anthropic()  # uses ANTHROPIC_API_KEY from env

# -----------------------------------------------------------
# STEP 1: The tools — what the agent can do
# -----------------------------------------------------------
# These are regular Python functions. The agent doesn't execute
# them directly; it "requests" them and the system runs them.

def get_weather(city: str) -> str:
    """In production, this would call a real weather API."""
    data = {
        "Buenos Aires": "22°C, partly cloudy",
        "Barcelona":    "18°C, sunny",
        "Madrid":       "25°C, clear"
    }
    return data.get(city, f"No data for {city}")

def calculate(expression: str) -> str:
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

def run_tool(name: str, params: dict) -> str:
    if name == "get_weather":
        return get_weather(params["city"])
    elif name == "calculate":
        return calculate(params["expression"])
    return "Tool not found"

# We tell the model what tools exist and how to use them
tools = [
    {
        "name": "get_weather",
        "description": "Gets the current weather for a city",
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "City name"}
            },
            "required": ["city"]
        }
    },
    {
        "name": "calculate",
        "description": "Evaluates a math expression. E.g.: '15 * 3 + 7'",
        "input_schema": {
            "type": "object",
            "properties": {
                "expression": {"type": "string"}
            },
            "required": ["expression"]
        }
    }
]

# -----------------------------------------------------------
# STEP 2: The agent loop — all the logic lives here
# -----------------------------------------------------------
def agent_loop(task: str):
    print(f"\n>>> Task: {task}\n")
    messages = [{"role": "user", "content": task}]

    while True:

        # ★★★ THIS IS THE KEY CALL ★★★
        # We send the task to the LLM along with the list of tools.
        # The model doesn't execute anything — it reasons and tells
        # us what it wants to do next.
        # It can reply with text (done) or request a tool (loop continues).
        response = client.messages.create(
            model="claude-opus-4-6",
            max_tokens=1024,
            tools=tools,        # ← the model knows what tools it has
            messages=messages   # ← the full conversation history
        )
        # ★★★★★★★★★★★★★★★★★★★★★★★★★★★

        # Did the model finish? Print the final response and exit.
        if response.stop_reason == "end_turn":
            final = next(b.text for b in response.content if hasattr(b, "text"))
            print(f"✓ Final answer: {final}")
            break

        # Did the model request a tool? We run it.
        tool_use   = next(b for b in response.content if b.type == "tool_use")
        tool_name  = tool_use.name
        tool_params = tool_use.input

        print(f"  → Model requested: {tool_name}({tool_params})")
        tool_result = run_tool(tool_name, tool_params)
        print(f"  ← Result:          {tool_result}\n")

        # Send the result back to the model and continue the loop
        messages.append({"role": "assistant", "content": response.content})
        messages.append({
            "role": "user",
            "content": [{
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": tool_result
            }]
        })

# -----------------------------------------------------------
# Run the agent
# -----------------------------------------------------------
agent_loop("What's 15% of 340? Also, how's the weather in Madrid?")

What's happening here?

The LLM call is the heart of the system (marked with ★). In that line, we pass the task and the list of available tools. The model responds in one of two ways: either with text (task finished) or by requesting a tool. If it requests a tool, we execute it, return the result, and call the model again. That cycle repeats until the model has everything it needs to give a final answer.

For this particular task, the agent will make two tool calls — one for the calculation, one for the weather — before returning a single final message with both answers.

What Agents Are Not (and Why It Matters)

With so much hype around the topic, it's worth being honest:

They're not infallible. Agents make mistakes. If the model makes a wrong decision in step 2, the error can propagate through the entire loop. That's why design matters — you need to think carefully about what tools you give them and what limits you set.

They're not autonomous by default. An agent does what you tell it to do, within the context you give it. It has no goals of its own, no initiative beyond the assigned task.

They don't replace human judgment. At least not yet. The best use cases are ones where the agent does the heavy lifting and a human reviews or approves the final result. Oversight is still key.

Where to Start

If you want to experiment with agents, my recommendation is to start simple: think of a repetitive task you do often — a report, a query, a notification. Identify what "tools" an agent would need to do that task (what data does it query? what systems does it access?). Then build a minimal version with Python and a model API. You don't need complex frameworks to get started.

The biggest conceptual leap isn't in the code — it's in changing how you think about tasks. From "I'll ask the model" to "I'll give the model a task and let it decide how to solve it."

IA Agents Python
· Mayo 2026 · 10 min de lectura

Todo el mundo habla de los agents. ¿Qué son y cómo puedo tener los míos?

Hace unos meses empecé a escuchar la palabra "agent" en todos lados. En LinkedIn, en podcasts, en reuniones de trabajo. Todo el mundo hablando de "agentes de IA" como si fuera la próxima gran revolución, pero muy pocos explicando qué significa en la práctica.

Yo mismo tardé un tiempo en entenderlo bien. No porque sea un concepto difícil, sino porque la mayoría de las explicaciones caen en uno de dos extremos: o son tan abstractas que no te dicen nada, o son tan técnicas que perdés el hilo a los dos minutos.

Este post es el que me hubiera gustado leer cuando empecé. Vamos por partes.

La diferencia que importa: chatbot vs. agent

Un chatbot responde. Un agent actúa.

Cuando le hacés una pregunta a ChatGPT, te da una respuesta. Eso es todo. No hace nada en el mundo real, no consulta tus sistemas, no ejecuta tareas. Es una conversación, muy inteligente, pero solo una conversación.

Un agent, en cambio, puede hacer cosas. Puede consultar una base de datos, mandar un mail, ejecutar un script, llamar a una API, guardar un archivo. Tiene acceso a herramientas, y las usa para completar objetivos.

La diferencia no está en el modelo de IA en sí — es la misma tecnología de base. La diferencia está en cómo está construido el sistema alrededor del modelo.

Los tres ingredientes de cualquier agent

No importa cuán complejo sea un agent, siempre tiene estos tres componentes:

1. Un modelo que razona (el cerebro). Es el LLM — GPT-4, Claude, Gemini, el que sea. Su trabajo es entender la tarea, decidir qué hacer, y generar respuestas. Pero por sí solo, no puede hacer nada fuera de la conversación.

2. Herramientas que puede usar (las manos). Son funciones reales que el modelo puede invocar: buscar en una base de datos, llamar a una API externa, leer un archivo, mandar una notificación. El modelo no las ejecuta directamente — le dice al sistema "quiero usar esta herramienta con estos parámetros", y el sistema lo hace.

3. Un loop de razonamiento (el ciclo). Acá está la clave. Un agent no responde una vez y termina. Sigue un ciclo:

Recibe una tarea
  → Razona: ¿qué necesito para resolver esto?
  → Usa una herramienta
  → Observa el resultado
  → ¿Ya terminé? No → sigue razonando
  → ¿Ya terminé? Sí → responde

Este loop es lo que lo hace "agente". Puede tomar múltiples pasos, adaptarse a resultados intermedios, y llegar a un objetivo sin intervención humana en cada paso.

Casos de uso reales — los que ya están pasando

Basta de teoría. Acá van tres ejemplos concretos del tipo de agents que se usan hoy.

1. Agent de monitoreo de datos

Imaginate que tenés una métrica importante en tu base de datos — ventas diarias, usuarios activos, lo que sea. Un agent puede consultar esa métrica cada mañana, compararla con el día anterior, y si hay una variación anormal, mandarte una alerta con el contexto: "Las ventas de hoy son un 40% menores al promedio de los últimos 7 días. Los productos más afectados son X e Y." No solo te avisa que algo pasó. Te explica qué pasó.

2. Agent de soporte interno

En muchas empresas, el equipo de soporte responde las mismas preguntas una y otra vez: cómo resetear una contraseña, cuál es el proceso para X, dónde está el documento Y. Un agent conectado a la base de conocimiento de la empresa puede responder esas preguntas automáticamente, consultar los sistemas internos cuando necesita datos en tiempo real, y escalar al humano solo cuando genuinamente no sabe la respuesta.

3. Agent de reporting semanal

Cada lunes hay que armar el reporte de la semana. Datos de diferentes fuentes, un análisis, las métricas clave. Un agent puede hacer ese trabajo: consulta las fuentes, agrega los datos, genera el texto del análisis, y manda el mail. Lo que antes llevaba dos horas, ahora pasa en cinco minutos sin que nadie lo supervise.

Veamos el código: un agent simple en Python

Para que no quede solo en teoría, acá hay un ejemplo real y funcional de cómo construir un agent. Solo Python y la API de Claude — sin frameworks, sin magia negra.

La idea: un agent que puede usar dos herramientas — consultar el clima y hacer cálculos. Le damos una tarea en lenguaje natural y él decide cómo resolverla.

import anthropic
import json

client = anthropic.Anthropic()  # usa ANTHROPIC_API_KEY del entorno

# -----------------------------------------------------------
# PASO 1: Las herramientas — lo que el agent puede hacer
# -----------------------------------------------------------
# Son funciones Python normales. El agent no las ejecuta
# directamente; las "pide" y el sistema las ejecuta por él.

def get_weather(city: str) -> str:
    """En producción, esto llamaría a una API real de clima."""
    data = {
        "Buenos Aires": "22°C, parcialmente nublado",
        "Barcelona": "18°C, soleado",
        "Madrid": "25°C, despejado"
    }
    return data.get(city, f"No tengo datos para {city}")

def calculate(expression: str) -> str:
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

def run_tool(name: str, params: dict) -> str:
    if name == "get_weather":
        return get_weather(params["city"])
    elif name == "calculate":
        return calculate(params["expression"])
    return "Herramienta no encontrada"

# Le decimos al modelo qué herramientas existen y cómo usarlas
tools = [
    {
        "name": "get_weather",
        "description": "Obtiene el clima actual de una ciudad",
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "Nombre de la ciudad"}
            },
            "required": ["city"]
        }
    },
    {
        "name": "calculate",
        "description": "Evalúa una expresión matemática. Ej: '15 * 3 + 7'",
        "input_schema": {
            "type": "object",
            "properties": {
                "expression": {"type": "string"}
            },
            "required": ["expression"]
        }
    }
]

# -----------------------------------------------------------
# PASO 2: El loop del agent — acá vive toda la lógica
# -----------------------------------------------------------
def agent_loop(task: str):
    print(f"\n>>> Tarea: {task}\n")
    messages = [{"role": "user", "content": task}]

    while True:

        # ★★★ ESTA ES LA LLAMADA CLAVE ★★★
        # Le mandamos la tarea al LLM junto con la lista de herramientas.
        # El modelo no ejecuta nada — razona y nos dice qué quiere hacer.
        # Puede responder con texto (terminó) o pedirnos que ejecutemos
        # una herramienta (sigue el loop).
        response = client.messages.create(
            model="claude-opus-4-6",
            max_tokens=1024,
            tools=tools,        # ← el modelo sabe qué herramientas tiene
            messages=messages   # ← todo el historial de la conversación
        )
        # ★★★★★★★★★★★★★★★★★★★★★★★★★★★

        # ¿El modelo terminó? Muestra la respuesta final y sale.
        if response.stop_reason == "end_turn":
            final = next(b.text for b in response.content if hasattr(b, "text"))
            print(f"✓ Respuesta final: {final}")
            break

        # ¿El modelo quiere usar una herramienta? La ejecutamos nosotros.
        tool_use    = next(b for b in response.content if b.type == "tool_use")
        tool_name   = tool_use.name
        tool_params = tool_use.input

        print(f"  → El modelo pidió: {tool_name}({tool_params})")
        tool_result = run_tool(tool_name, tool_params)
        print(f"  ← Resultado:       {tool_result}\n")

        # Le devolvemos el resultado al modelo y seguimos el loop
        messages.append({"role": "assistant", "content": response.content})
        messages.append({
            "role": "user",
            "content": [{
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": tool_result
            }]
        })

# -----------------------------------------------------------
# Probemos el agent
# -----------------------------------------------------------
agent_loop("¿Cuánto es el 15% de 340? Y de paso, ¿cómo está el clima en Madrid?")

¿Qué está pasando acá?

La llamada al LLM es el corazón del sistema (marcada con ★). En esa línea, le pasamos la tarea y la lista de herramientas disponibles. El modelo responde de dos formas posibles: o con texto (tarea terminada) o pidiendo ejecutar una herramienta. Si pide una herramienta, nosotros la ejecutamos, le devolvemos el resultado, y volvemos a llamar al modelo. Ese ciclo se repite hasta que el modelo tiene toda la información que necesita para responder.

Para esta tarea en particular, el agent va a hacer dos llamadas de herramienta — una para el cálculo, otra para el clima — antes de darte la respuesta final en un solo mensaje.

Lo que los agents no son (y por qué importa decirlo)

Con tanto hype alrededor del tema, vale la pena ser honesto:

No son infalibles. Los agents cometen errores. Si el modelo toma una decisión equivocada en el paso 2, el error se puede propagar por todo el loop. Por eso el diseño importa — hay que pensar bien qué herramientas les damos y qué límites les ponemos.

No son autónomos por defecto. Un agent hace lo que le decís que haga, dentro del contexto que le diste. No tiene objetivos propios ni iniciativa más allá de la tarea asignada.

No reemplazan el criterio humano. Al menos no todavía. Los mejores casos de uso son aquellos donde el agent hace el trabajo pesado y un humano revisa o aprueba el resultado final. La supervisión sigue siendo clave.

¿Por dónde empezar?

Si querés experimentar con agents, mi recomendación es empezar simple: pensá en una tarea repetitiva que hacés seguido — un reporte, una consulta, una notificación. Identificá qué "herramientas" necesitaría un agent para hacer esa tarea (¿qué datos consulta? ¿a qué sistemas accede?). Después construí una versión mínima con Python y la API de un modelo. No necesitás frameworks complejos para empezar.

El salto conceptual más grande no está en el código — está en cambiar la forma en que pensás las tareas. De "le pregunto al modelo" a "le doy una tarea al modelo y él decide cómo resolverla".

¿Tenés una tarea repetitiva en tu trabajo que podría automatizar un agent? Contame en los comentarios.
